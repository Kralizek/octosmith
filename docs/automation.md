# Automation

Octosmith can run through the repository-level GitHub Action or through
workflows generated by the control-repository scaffolder.

## GitHub Action

```yaml
- uses: actions/checkout@v7
- uses: Kralizek/octosmith@v0
  with:
    mode: apply
    github-token: ${{ secrets.OCTOSMITH_TOKEN }}
```

Supported modes are `validate`, `plan`, and `apply`.

`validate` does not require GitHub credentials. `plan` and `apply` do.

The Action uses `resource` for the optional plan/apply target, matching the
CLI's generic resource terminology. Set `trace: true` to emit GitHub API request
traces separately from `verbose: true`, which only expands report detail.

The Action resolves the exact `@octosmith/cli` version recorded in its release
commit and runs that published JSR package. Moving Action tags such as `v0` and
`v0.x` are updated only after the matching CLI package has been published.

Fresh plan/apply obey `repositories.settings.secrets` (`automatic` by default,
or `manual` to preserve secrets without requiring their runtime sources). The
Action's optional `include-secrets` input accepts `"true"` and `"false"`:

```yaml
- uses: Kralizek/octosmith@v0
  with:
    mode: apply
    github-token: ${{ secrets.OCTOSMITH_TOKEN }}
    include-secrets: ${{ inputs.include-secrets }}
```

For a directly installed CLI, optional booleans support CI parameterization:

```yaml
- name: Apply Octosmith configuration
  run: |
    octosmith apply \
      --path ./github \
      --include-secrets=${{ inputs.include-secrets }}
```

The bare CLI flag and `=true` explicitly include all supported secrets alongside
other resources. `=false` honors the configured mode, so it does not disable
secrets in automatic mode. Only literal `true` and `false` are valid explicit
values. `--skip-missing-values` remains independent. Persisted `apply --plan`
ignores this flag and the current secret-mode policy for operation selection; it
executes only the reviewed stored operations with the existing safety checks.

## Credentials

The credential is exposed to the CLI through `GITHUB_TOKEN`; it is not passed as
a CLI argument.

The token needs read permissions for resources used by plan and corresponding
write permissions for resources managed by apply.

For long-lived organization automation, prefer a GitHub App installation token
minted at workflow runtime over a static broad token where practical.

## Repository creation permissions

`octosmith template permissions services --creation --format json` (or text)
analyzes creation separately from ordinary plan/apply. The output separates:

- **Organization repository creation authorization:** the organization endpoint
  requires repository Administration: write for fine-grained PATs/GitHub Apps.
  This is a repository permission used for an organization-level operation, not
  a fabricated organization Administration permission. Classic PATs require
  `repo` for private/internal repositories or `public_repo` for public ones. The
  authenticated actor must be allowed to create the requested visibility.
- **Selector metadata:** team assignment requires repository Administration:
  write, organization Members: read and metadata access. Repository custom
  property assignment requires Custom properties: write. Definitions must
  already exist, allow the chosen values, and permit repository-level editing.
- **Reconciliation:** normal configured resource permissions, including deferred
  API work, plus Contents: read to inspect history.
- **Initial Git bootstrap:** Contents: write, plus Workflows: write for present
  workflow files. Classic PATs also need the appropriate `repo`/`public_repo`
  and `workflow` scopes. No Pull requests: write is needed for creation, even
  when ongoing file delivery uses pull requests. The same token conventions
  apply, but API creation authorization does not guarantee Git push access.

Organization/enterprise restrictions, SAML SSO authorization, visibility policy,
enterprise-only internal visibility and installation repository selection can
still reject a valid offline specification. Ensure a GitHub App installation can
access the newly created repository as well as invoke creation. Permission
analysis is not a guarantee of authorization. Ordinary `template permissions`,
plan and apply do not gain creation-specific authorization requirements.

After creation, missing teams/properties or failed classification may leave the
repository outside management scope. Repair these manually before relying on
ordinary discovery/apply. Reconciliation failures after successful verification
can be repaired by fresh plan/apply. Repositories are never automatically
deleted. Creation makes one local Git commit and at most one push;
default-branch work, all rulesets and archival follow a confirmed push, with
archival last. Inspect branch/SHA before recovering an uncertain push; never
rerun create for a retained repository. See
[creation recovery](../packages/cli/README.md#resource-create). Ordinary apply
retains its existing bootstrap behavior.

## Generated workflows

The scaffolder generates:

- pull-request validation with no organization credential
- default-branch apply with `cancel-in-progress: false`

The generated apply workflow expects an `OCTOSMITH_TOKEN` repository secret.

## Event streaming

`plan` and `apply` can emit NDJSON repository events through `--events-output`.

The destination may be a regular file, FIFO, or another writable path.

- plan emits `resource.planned`
- apply emits `resource.applied`
- successful managed PR operations emit `pull_request.opened`,
  `pull_request.updated`, or `pull_request.closed` during apply

PR events precede repository completion and use the same canonical lifecycle
result as apply JSON. An untouched PR emits no lifecycle event. Successful
outcomes remain in the final report even if a later step or repository fails.

A lifecycle event confirms a **completed action**, not successful completion of
the entire repository reconciliation:

- `opened`: GitHub created the PR, its head/base and generated metadata are
  confirmed, and target/head/lock validation succeeds afterward.
- `updated`: the desired branch and PR title/generated section are confirmed
  after the last required core change. An intermediate branch replacement alone
  never qualifies. For a labels-only change, the label write and current PR
  state must also be confirmed.
- `closed`: an authoritative empty delta was validated immediately before the
  close request, GitHub confirmed closure, and subsequent state validation
  succeeded.

Labels are ancillary to an already completed creation or core metadata update.
For example, a body-update failure after branch replacement emits nothing, but a
label failure after a confirmed body update retains `updated`. A newly opened PR
retains `opened` if label assignment fails; it does not also emit `updated`. A
completed closure retains `closed` if lock cleanup fails. The repository report
and exit status still indicate failure, including any later target drift.
Consumers must use `resource.applied` and the final report to determine overall
reconciliation success. Each PR contributes at most one lifecycle event per
apply.

For example, a closure event is one NDJSON line:

```json
{
  "type": "pull_request.closed",
  "timestamp": "2026-10-09T12:00:00.000Z",
  "source": { "kind": "github.organization", "id": "example-org" },
  "subject": { "kind": "github.pull_request", "id": "service-api#123" },
  "metadata": { "producer": "octosmith" },
  "data": {
    "repository": "service-api",
    "number": 123,
    "url": "https://github.com/example-org/service-api/pull/123",
    "action": "closed",
    "reason": "no_differences"
  }
}
```

Events contain no managed-file contents, patches, or secrets. Plan only emits
`resource.planned`, including when a zero-operation plan may require apply-time
PR cleanup.

When scaffolding with `--event-streaming`, Octosmith generates a Hooksmith
example. Hooksmith runs in a Deno container, receives events through stdin, and
is not given the Octosmith GitHub credential.

The workflow supervises Octosmith and Hooksmith together so failure or
cancellation does not leave a credentialed apply process running.
